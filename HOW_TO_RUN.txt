ZK-KGVerify — how to run everything
===================================

TL;DR
-----
    pip install -r requirements.txt
    python run_all.py --private-key 0xYOUR_SEPOLIA_TESTNET_KEY

That is the only input needed. An RPC endpoint is chosen automatically from a
list of public Sepolia nodes, the contract is compiled and deployed, the model
is registered on-chain, proofs are generated from real model predictions,
every proof is verified inside the EVM, and every number quoted in the paper
is regenerated into results/.


BEFORE YOU START
----------------
1. Use a THROWAWAY account. Create a fresh account in MetaMask, and put only
   free Sepolia testnet ETH in it. Never use a key that holds mainnet funds.

   The key is never printed, never logged, and never written to disk. The
   secret commitment opening is stripped from results before anything is
   saved.

2. Fund it (free, takes a minute):
       https://sepoliafaucet.com
       https://www.alchemy.com/faucets/ethereum-sepolia
       https://faucet.quicknode.com/ethereum/sepolia

   You need roughly 0.05 Sepolia ETH for 30 records plus deployment.
   The script refuses to start with a zero balance and tells you where to go.

3. Export the key to your MetaMask account:
       MetaMask -> account menu -> Account details -> Show private key

   You can pass it on the command line or set it in the environment:

       PowerShell:  $env:SEPOLIA_PRIVATE_KEY = "0x..."
       bash:        export SEPOLIA_PRIVATE_KEY=0x...


CHECK IT WORKS FIRST (no key, no money, ~2 minutes)
---------------------------------------------------
    python run_all.py --profile smoke --stages selftest,local-evm

This runs the cryptographic self-tests and deploys the contract to an
in-memory EVM, verifying honest proofs and rejecting every adversary class.
If this passes, the on-chain path will work.


PROFILES
--------
  --profile smoke   ~2 min, CPU. End-to-end sanity check, 3 on-chain records.
  --profile fast    ~1-2 h, CPU. Reduced epochs. Real numbers, not paper-grade.
  --profile paper   Full protocol. NEEDS A GPU. This is the Colab config:
                    4 models x 2 datasets, 200 epochs, full test sets,
                    1000 proofs, 30 on-chain records.

On a CPU-only machine the 'paper' profile will take many hours of training.
Run training on Colab (T4 is enough), then bring the checkpoints back and run
only the on-chain stage locally — see "SPLITTING THE WORK" below.


STAGES
------
Everything except 'sepolia' runs without a private key.

    selftest   crypto self-tests: binding, vacuity, completeness,
               soundness (6 adversaries), HVZK
    local-evm  deploy + verify on an in-memory EVM; measures gas
    train      train and evaluate the KG embedding models
    zkp        proof benchmark on real model embeddings
    sepolia    deploy to Sepolia, register the model, submit records
    report     figures, LaTeX tables, and paper macros

Run a subset:
    python run_all.py --stages selftest,local-evm,train,zkp,report
    python run_all.py --private-key 0x... --stages sepolia,report

State carries across invocations, so a later `--stages report` still sees
results produced by an earlier run.


SPLITTING THE WORK (recommended)
--------------------------------
Train on a GPU, submit from anywhere:

  On Colab (GPU):
      python run_all.py --profile paper --stages train,zkp,report
      # then download checkpoints/ and results/

  Locally (needs only the key):
      python run_all.py --private-key 0x... --profile paper \
             --stages sepolia,report

Training checkpoints are reused automatically; pass --no-resume to retrain.


WHAT TO EXPECT ON-CHAIN
-----------------------
  - one deployment transaction
  - one registerModel transaction (single-shot per model id)
  - N verifyAndLog transactions, ~12 s apiece on Sepolia

Records are only created if the EVM itself validates the proof. An invalid
proof reverts and produces no record — that is the point of the design.

If you re-run against the same contract, use --attach 0xADDRESS to skip
redeployment. Registration is single-shot: re-running with the same model id
and the same commitment is fine; a *different* commitment is refused, because
allowing it would let a model be swapped after predictions were published.


VERIFYING SOMEONE ELSE'S RUN (no key needed)
--------------------------------------------
    python tools/fetch_onchain_log.py --address 0xCONTRACT
        Rebuilds the complete audit log straight from the chain.

    python tools/check_onchain_parity.py --address 0xCONTRACT --model-id CompGCN
        Confirms the deployed contract's generator and digest derivations
        match this repository's, and that it rejects forged proofs.


TROUBLESHOOTING
---------------
"has 0 Sepolia ETH"
    Fund the account at a faucet listed above.

"No usable Sepolia RPC"
    Public nodes rate-limit. Get a free Alchemy or Infura key and pass
    --rpc https://eth-sepolia.g.alchemy.com/v2/YOUR_KEY

"nonce too low" / "already known"
    Handled automatically: the client resyncs from the pending nonce once.
    If it persists, wait for pending transactions to clear and re-run.

"Generator mismatch between contract and src/zkp_module.py"
    The deployed contract was compiled from different constants. Deploy a
    fresh one (drop --attach).

"Model is already registered with a different commitment"
    Expected and deliberate. Use a new --model-id or deploy a new contract.

solc download fails
    py-solc-x fetches solc 0.8.20 on first use. Behind a proxy, install it
    once manually:  python -c "import solcx; solcx.install_solc('0.8.20')"


OUTPUTS
-------
    results/all_results.json          everything, one file
    results/sepolia_log.json          on-chain records with gas and cost
    results/onchain_verifier_test.json  local EVM verification + gas
    results/zkp_benchmark.json        proof timings and soundness
    results/link_prediction.json      MRR / Hits@K per model per dataset
    results/paper_macros.tex          every paper number, as LaTeX macros
    results/*.png, *.pdf              figures
    results/table_*.tex               LaTeX tables

The manuscript reads paper_macros.tex directly, so regenerating results
updates the paper. Check that nothing drifted:

    python tools/check_paper_numbers.py \
        --tex ../Submission_ClusterComputing/sn-article.tex
