## What I found

### 1. The commitment scheme was not binding (fatal)

The second Pedersen generator was `H = h·G` with `h = SHA256(tag)` public.
Because `h` is public, `C = vG + rH = (v + rh)G`, so any commitment reopens to
any value:

```
r' = (v − v')·h⁻¹ + r   (mod n)
```

One modular inverse and the commitment means nothing. I reproduced the attack
against the old code — it opened the same `C` to both `123456789` and `42`.

The old test suite passed anyway, because completeness, zero-knowledge, and
the tamper test do not exercise binding. **Fixed** by deriving `H` via
hash-to-curve, so nobody knows its discrete log. `selftest_binding()` now runs
the attack as a regression test.

### 2. The protocol proved nothing (also fatal, and subtler)

The old code created a **fresh commitment for every prediction** and then
proved it knew the opening. But the prover chose the committed value itself,
so of course it knows the opening — a random vector would have produced an
equally valid proof. Every primitive was correct and the composed statement
was empty.

**Fixed** by registering one commitment to the trained weights *before* any
query is served, on-chain, where consensus timestamps it. Every proof now
opens that registered commitment.

### 3. The blockchain verified nothing

The old contract stored a `verified` boolean the caller supplied. A dishonest
prover could log `verified = true` for a proof that never validated.

**Fixed** with a new contract that runs the Schnorr check inside the EVM using
the alt_bn128 precompiles and reverts on failure. This is now the paper's
headline result: **on-chain verification costs only +4.1% gas** over logging
an unchecked boolean.

### 4. The on-chain records were synthetic

`run_sepolia.py` generated proofs over random vectors, not real model
predictions. **Fixed** — proofs now come from genuine predictions of a trained
model, and the model's weight digest is recorded with them.

### 5. The paper cited 30 on-chain records; the repo shipped 15

I checked the chain: the contract really does hold 30 records, the deployment
gas really is 545,765, and the steady-state 236,955 ± 173 gas figure is
correct. The shipped log was just incomplete. Only `0.0376 ETH` was wrong
(actual: `0.0326`). **Fixed**, and I added `tools/fetch_onchain_log.py` so
anyone can rebuild the log straight from the chain.

To stop this recurring, every number in the paper is now generated by the
code as a LaTeX macro; `tools/check_paper_numbers.py` fails if the manuscript
contains a hand-typed figure.
